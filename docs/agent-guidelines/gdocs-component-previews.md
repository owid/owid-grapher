# Component preview images in Google Docs

Chart and image components in a gdoc are just text (`{.chart}` / `url: …` / `{}`), so authors paste a PNG of the chart or image right above the component to see what they're writing about. Those PNGs go stale when the chart or image changes. `db/model/Gdoc/componentPreviews/` keeps them current by writing into the Google Doc itself.

## How it works

1. **Find components** (`componentPreviewBlocks.ts`) — walks the raw Docs API document in _all_ tabs (fetched with `includeTabsContent: true`, unlike ingestion, which only reads the first tab), including table cells. The components it looks for are listed in `COMPONENT_TARGETS`, which is typed against the raw ArchieML block types, so its property names can't drift from what ingestion parses: `{.chart}` / `{.narrative-chart}` objects and their single-line forms (`chart: <url>`, `narrative-chart: <name>`), `{.key-indicator}` (renders its `datapageUrl` chart), `{.image}` (by `filename`), `{.static-viz}` (by `name`) and `{.pull-chart}` (shows its uploaded `image` thumbnail, not a render of its url). The `chart:` slides of a `[.chart-story]` read as the single-line chart form. The preview image is the last inline image of the closest non-blank paragraph above the component, either in its own paragraph or at the end of a text paragraph. Some authors put the image below the component instead. For a component without an image above, the first thing after its closing `{}` (or its single line), skipping blank lines, is recorded as `imageBelow` if it's an image, unless it is the image above another component. Such images are reported (so authors can move them) but never changed, and the component doesn't get a new image either: previews belong above the component, and keeping one convention keeps docs predictable to parse. Where it matters, the doc is read the way ingestion reads it: suggestions are accepted with `acceptAllGdocSuggestions`, which keeps the elements' indices, so they still address the suggestions-inline view that writes use; and URL values go through `gdocToArchie`'s span serialisation and `extractUrl`, so linked text and smart chips resolve to their link target.
2. **Resolve the image URL** (`componentPreviewSources.ts`) — maps each component to a public PNG. `/grapher/` and `/explorers/` links resolve through `resolveGdocLinkTargets` (`db/model/Gdoc/gdocLinkTargets.ts`), the same resolver the gdoc's linked charts use, so the image shows what the article's link shows. The one difference is opt-in: previews also fall back to draft charts, and flag them in the result because the article treats such links as broken until the chart is published. Standalone charts render via `/grapher/by-uuid/<configId>.png` (so drafts work too) plus the link's query string. Multi-dims (by slug, or an old chart slug that redirects to one via `multi_dim_redirects`, resolved in the same order as on the site) render the grapher config of the view the query params select, `/grapher/by-uuid/<view fullConfigId>.png`, with the dimension params dropped. Narrative charts render their merged config, `/grapher/by-uuid/<narrative_charts.chartConfigId>.png`. Explorers render from their published page, `/explorers/<slug>.png?<query>`, so only published explorers work; explorers that redirect to a multi-dim pick the `multi_dim_redirects` rule matching the link's query params, and the rule's params win over the link's, like the site's explorer redirects (grapher slugs redirect to one target whatever the query params, here and on the site). The URL ends in `v=<hash>`, a hash of the config's `configMd5` and the `dataChecksum`/`metadataChecksum` of the indicators it uses. For explorers the hash covers the explorer config, the configs of all its `explorer_views`, and the checksums of its indicators (direct and via `explorer_charts`); these are aggregated in SQL with `BIT_XOR(CRC32(…))`. Data that explorers load from CSV files isn't covered. Images and static viz resolve to their current upload on Cloudflare Images (`CLOUDFLARE_IMAGES_URL/<cloudflareId>/w=<width>`), which is shared by all environments; replacing an image uploads a new `cloudflareId`, so these URLs need no version hash.
3. **Diff and write** (`refreshGdocComponentPreviews.ts`) — Google records the URL an image was inserted from as `sourceUri`, so an image is up to date when its `sourceUri` equals the URL we'd insert now and its frame in the doc has the image's shape (within 2%). We don't need our own bookkeeping table. Each source knows its aspect ratio: chart renders are 850×600 (unless the link has `im*` size params, in which case the shape isn't checked), uploaded images use their original dimensions. Outdated or hand-pasted images are swapped with `replaceImage`, which keeps the object id and the size in the doc but center-crops into that frame. We prefer it because keeping the object id keeps comments anchored on the image (verified: they survive `replaceImage` but not a reinsert), and keeps a size the author chose. The flip side is that a comment about the old image stays attached to the new one. When the image's shape differs from the frame, which also catches a current image in a wrong frame, it's deleted and inserted again at the same position and width instead, getting a new object id and losing its comments. Components without an image get one in a new paragraph above. There are no options: every entry point applies the same rules, so docs stay consistent. Each URL is fetched once beforehand. That warms the Cloudflare cache and catches broken renders, because a single URL Google can't fetch fails the whole `batchUpdate`. If the batch fails anyway, each change is retried on its own. All writes target the revision we read, so Google adjusts positions for edits authors make meanwhile.

Inline images are ignored by `gdocToArchie`, so none of this affects ingestion.

## Entry points

- Admin: "Update preview images in gdoc" in the gdoc preview page's ⋮ menu, and an image button (labelled on hover) on each row of the gdocs list (one shared `GdocsComponentPreviewsModal` in `GdocsList`). Opening the modal runs a dry run and shows what would change per component; "Update" writes, closes the modal and reports the result in a notification, with Retry when some images failed (rendering is only checked on write; retrying is safe since up-to-date images are skipped). Both call `POST /api/gdocs/:gdocId/refreshComponentPreviews` with `{ dryRun }`.
- CLI / cron: `yarn refreshGdocComponentPreviews [--dry-run] [--changed-since-hours <n>] [gdocId…]`. `--changed-since-hours` selects the gdocs whose chart, chart story, key indicator or narrative chart components point to charts, multi-dims, narrative charts or explorers whose config or data changed recently, or whose slug's multi-dim redirects were added or edited (via `posts_gdocs_links`), or use images or static viz that were replaced (via `posts_gdocs_x_images` and `posts_gdocs_links`). This is generous, but docs whose images are current cost only a read.

## Settings and local testing

Google fetches the images itself, so their base URL must be public. `GDOCS_CHART_PREVIEW_GRAPHER_URL` and `GDOCS_CHART_PREVIEW_EXPLORER_URL` therefore default to production (`https://ourworldindata.org/grapher` / `/explorers`) in every environment. A staging server can't even reach its own thumbnail URL from inside its container. Config ids are the same as in production for charts that exist there, so the images render correctly. Charts and multi-dims that only exist in a local or staging DB fail with a 404 from production. To resolve charts newer than your local DB, point the script at a recent staging DB with `STAGING=<branch>`; it only reads from the DB.
