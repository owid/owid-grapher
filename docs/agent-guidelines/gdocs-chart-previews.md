# Chart preview images in Google Docs

Chart components in a gdoc are just text (`{.chart}` / `url: …` / `{}`), so authors paste a PNG of the chart right above the component to see what they're writing about. Those PNGs go stale when the chart changes. `db/model/Gdoc/chartPreviews/` keeps them current by writing into the Google Doc itself.

## How it works

1. **Find components** (`chartPreviewBlocks.ts`) — walks the raw Docs API document in _all_ tabs (fetched with `includeTabsContent: true`, unlike ingestion, which only reads the first tab), including table cells. It matches `{.chart}` / `{.narrative-chart}` objects and their single-line forms (`chart: <url>`, `narrative-chart: <name>`). The preview image is the last inline image of the closest non-blank paragraph above the component, either in its own paragraph or at the end of a text paragraph.
2. **Resolve the image URL** (`chartPreviewSources.ts`) — maps each component to a public PNG. Standalone charts render via `/grapher/by-uuid/<configId>.png` (so drafts work too) plus the link's query string. Multi-dims (by slug, or an old chart slug that redirects to one via `multi_dim_redirects`, resolved in the same order as on the site) render the grapher config of the view the query params select, `/grapher/by-uuid/<view fullConfigId>.png`, with the dimension params dropped. Narrative charts render their merged config, `/grapher/by-uuid/<narrative_charts.chartConfigId>.png`. Explorers render from their published page, `/explorers/<slug>.png?<query>`, so only published explorers work; explorers that redirect to a multi-dim resolve like grapher redirects. The URL ends in `v=<hash>`, a hash of the config's `configMd5` and the `dataChecksum`/`metadataChecksum` of the indicators it uses. For explorers the hash covers the explorer config, the configs of all its `explorer_views`, and the checksums of its indicators (direct and via `explorer_charts`); these are aggregated in SQL with `BIT_XOR(CRC32(…))`. Data that explorers load from CSV files isn't covered.
3. **Diff and write** (`refreshGdocChartPreviews.ts`) — Google records the URL an image was inserted from as `sourceUri`, so an image is up to date exactly when its `sourceUri` equals the URL we'd insert now. We don't need our own bookkeeping table. Outdated or hand-pasted images are swapped with `replaceImage`, which keeps the object id and the size in the doc. With `insertMissing`, components without an image get one in a new paragraph above. Each URL is fetched once beforehand. That warms the Cloudflare cache and catches broken renders, because a single URL Google can't fetch fails the whole `batchUpdate`. If the batch fails anyway, each change is retried on its own. All writes target the revision we read, so Google adjusts positions for edits authors make meanwhile.

Inline images are ignored by `gdocToArchie`, so none of this affects ingestion.

## Entry points

- Admin: "Update chart images in gdoc" in the gdoc preview page's ⋮ menu, and an "Update chart images" button on each row of the gdocs list (one shared `GdocsChartPreviewsModal` in `GdocsList`). Both call `POST /api/gdocs/:gdocId/refreshChartPreviews`.
- CLI / cron: `yarn refreshGdocChartPreviews [--insert-missing] [--dry-run] [--changed-since-hours <n>] [gdocId…]`. `--changed-since-hours` selects the gdocs that link to charts, multi-dims, narrative charts or explorers whose config or data changed recently (via `posts_gdocs_links`). This is generous, but docs whose images are current cost only a read.

## Settings and local testing

Google fetches the images itself, so their base URL must be public. `GDOCS_CHART_PREVIEW_GRAPHER_URL` and `GDOCS_CHART_PREVIEW_EXPLORER_URL` therefore default to production (`https://ourworldindata.org/grapher` / `/explorers`) in every environment. A staging server can't even reach its own thumbnail URL from inside its container. Config ids are the same as in production for charts that exist there, so the images render correctly. Charts and multi-dims that only exist in a local or staging DB fail with a 404 from production. To resolve charts newer than your local DB, point the script at a recent staging DB with `STAGING=<branch>`; it only reads from the DB.
