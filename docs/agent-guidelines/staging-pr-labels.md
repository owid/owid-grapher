# Staging PR labels

Every owid-grapher PR gets a staging server (`staging-site-<branch>`), built by the Buildkite pipeline `grapher-automated-staging-environment`. A few PR labels switch on extra behaviour for that server. They are read by the staging scripts in the `owid/ops` repo (`templates/owid-site-staging/*.sh` and `templates/common.sh`; the user-facing list is in `templates/owid-site-staging/README.md` there) — if a label below seems not to do what it says, check those scripts, they are the source of truth.

Labels are read on every push, so adding a label later takes effect with the next commit. The exposure labels (`staging-https`, `staging-public`) can also be applied to a running server without a push via `staging-exposure.sh` in ops.

## When to add which label

Add labels when creating the PR (`gh pr create --label staging-viz …`) or afterwards (`gh pr edit <n> --add-label …`), and tell the user which ones you added and why. Only add a label when the PR's change actually calls for it — most PRs need none.

| Label               | What it does                                                                                                                                                                                                                      | Add it when                                                                                                                                                                                                                                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `staging-viz`       | The SVG tester soft-fails (marks "charts changed here") instead of going red when it finds SVG differences. It also forces the SVG tester to run even if no SVG-relevant path changed.                                            | The PR **intentionally** changes how charts render (grapher layout, styling, labels, axis logic, …). Don't add it to hide unexpected diffs. Without the label, the tester only runs when the branch touches `packages/@ourworldindata/{grapher,core-table,utils,types,components}/` or `devTools/svgTester/`. |
| `staging-viz-full`  | Runs the full SVG suite (graphers, grapher-views, mdims, thumbnails) instead of only graphers.                                                                                                                                    | The change can affect chart views with query params, multi-dims or thumbnails specifically — e.g. touching the multi-dim code, thumbnail rendering, or URL/query-param handling in grapher. Combine with `staging-viz` if differences are expected.                                                           |
| `staging-algolia`   | Builds a separate Algolia search index for the staging server during the bake (and deletes it when the PR closes).                                                                                                                | The PR changes Algolia indexing or search UI that needs real search results on staging (`baker/algolia/`, `site/search/`). Note `/search` 404s on staging without it — see the `test-on-staging` skill.                                                                                                       |
| `staging-typesense` | Installs a Typesense server on the staging container and builds its search index on every push.                                                                                                                                   | The PR works on the Typesense-based search.                                                                                                                                                                                                                                                                   |
| `staging-bespoke`   | Builds the bespoke viz bundles (`yarn buildBespoke`) so they're served in the Cloudflare content preview.                                                                                                                         | Rarely needed: a branch that touches `bespoke/` already builds them automatically. Add it only if the preview must show bespoke components without the branch changing `bespoke/` (e.g. testing a page that embeds one).                                                                                      |
| `staging-https`     | Serves the staging admin and site over tailnet-only HTTPS (`https://staging-site-<branch>.tail6e23.ts.net`) instead of plain `http://staging-site-<branch>`.                                                                      | The feature needs a secure context in the browser (clipboard API, service workers, `crypto.subtle`, secure cookies, …) or HTTPS for some other reason.                                                                                                                                                        |
| `staging-public`    | Makes the staging **site** (not the admin) publicly reachable on the internet via Tailscale Funnel, at the same `.ts.net` URL. Only the site server is exposed, so nginx-only routes such as `/assets/bespoke/` don't load there. | Only when the user explicitly wants to share the staging site with people outside the tailnet. Never add it on your own initiative — it publishes unreleased work.                                                                                                                                            |
| `staging-bake`      | Forces a full site bake and configures the staging admin to trigger bakes through Buildkite. owid-grapher PRs always get a full bake anyway, so this label mostly matters for ETL PRs.                                            | Rarely relevant in this repo; add it only if the user asks for Buildkite-triggered bakes from the staging admin.                                                                                                                                                                                              |

**`labs`** isn't a staging label but works through the same pipelines: it puts the PR on Labs (http://labs.owid.io, tailnet only), a staff-only copy of the site built from master plus every open PR with the label, rebuilt on every push to master or to a labelled PR (adding or removing the label takes effect with the next such push). Add it only when the user wants staff to try the feature during their work, and tell them; it's also a reason the stale bot leaves the PR open. How Labs works: the "Labs" section of `templates/owid-site-staging/README.md` in owid/ops.

Other `staging*` labels exist in the repo (`staging`, `staging-archive`) but the staging scripts don't read them; don't add them.
