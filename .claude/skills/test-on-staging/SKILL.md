# Testing on staging

- **When a push is live:** a staging server runs a push once the commit status `buildkite/grapher-automated-staging-environment/grapher-build` on that commit turns `success`, usually a minute or two after the push and a few more on a branch's first push, which creates the server. From then on it serves the new browser code and `functions/`, so that's when to test or hand over a link: earlier, the user reloads into the previous version. Read that one context, not the combined `state`, which waits for the whole build: `gh api repos/owid/owid-grapher/commits/<sha>/status --jq '.statuses[] | select(.context == "buildkite/grapher-automated-staging-environment/grapher-build") | .state'` (if `gh api` fails, `curl` the same public API), polled every ~20 s. `failure` or `error` means this push won't show up, so say so; if it hasn't turned `success` within ~10 minutes, or can't be read, say the server may still be building rather than keep waiting. Only a branch with an open PR gets built, so without one no status appears. Changes to HTML rendered on the server (article and chart pages) and to bespoke components need the bake too: wait for `…/grapher-bake` instead. The bake ends by restarting the site server, so requests to it fail for a few seconds then; retry before calling a change broken.
- **On Labs** (http://labs.owid.io) your commit's statuses belong to your PR's own server. Labs builds the `labs` branch (master plus every open PR with the `labs` label, see `docs/agent-guidelines/staging-pr-labels.md`), which owidbot rebuilds and force-pushes after each push to master or to such a PR: usually within a minute, much longer when it has to resolve a conflict. Adding the label starts nothing, so it shows with the next push. Wait until `git fetch -q origin labs && git merge-base --is-ancestor <sha> origin/labs` succeeds, then poll the status above on the newest `origin/labs` commit; a later force-push cancels the older build, so a `failure` on a commit that's no longer the tip says nothing about yours. If your PR doesn't arrive, the description of the Labs PR (`gh pr list --head labs`) lists the PRs left out of the build. Link labs.owid.io, not `staging-site-labs`: the site is built for that host, and its admin is switched off, so the admin tools below don't work there.
- `yarn tsx devTools/callAdminApi.ts get <chartId> --branch <branch>` / `set <chartId> '<jsonPatch>' --branch <branch>` / `unset <chartId> <field> --branch <branch>`: inspect or change a chart's config on any `staging-site-<branch>` (or `--host` for local/prod) without the browser.
- Auth is `ADMIN_API_KEY` in `.env` — one shared key works against **every** staging server (not per-branch), since `admin_api_keys` ships in the private data dump every staging build restores from (see `db/exportMetadataTables.ts`). It's the same key etl already uses; no need to mint a new one.
- `STAGING=1 yarn startAdminDevServer` runs the admin **locally against the current branch's staging database** (`STAGING=<branch>` for another branch's), so you see a code change on save instead of after a deploy and a bake. Staging MySQL listens on Tailscale, so it needs no tunnel and no extra credentials. Two things to keep in mind: it is read-write on a database other people may be testing against, and every query pays the round trip (~10x the local latency), so it is somewhere to check behaviour, not to measure performance. `STAGING` works for any server-side entry point, not just the admin.
- During the post-push rebake the staging box is saturated — load average ~250 on 16 cores — so anything timed in that window measures the bake, not the code. Check `pgrep -f buildLocalBake` over ssh before believing a slow number.
- Don't wait for the static-site rebake (~10-13 min) to check or share a chart — `http://staging-site-<branch>/admin/charts/<id>/preview` reflects both chart-config edits and pushed code changes within ~1-3 min. Default to this link (not the public `/grapher/<slug>` page) whenever pointing someone at a chart on staging.
- A branch's `/search` and `/api/search` work without any label: they search the shared, unprefixed indices (`pages`, `explorer-views-and-charts`, …) in the staging Algolia application, so a PR that only changes the search UI or the search API needs nothing. The `staging-algolia` label is for PRs that change what gets indexed (`baker/algolia/`): it builds a full index of the branch's own, prefixed `staging-site-<branch>-`, on every push. Each such index costs ~34k records of the staging application's shared record quota, and when that runs out every labelled bake fails with "You have exceeded your Record quota", so don't add the label just to get search results. Staging and production Algolia data live in **separate Algolia applications**, and ranking differs between them, so don't probe a staging index with production's `appId`/key to check whether it exists; test through the deployed `/search` or `/api/search`, which uses whatever env that deployment is configured with.
- `/search` deep links and screenshots: add `&resultType=all` (a bare URL can open on the Data tab and hide Data Insights/Writing), and dismiss the cookie banner first — it's fixed-position and lands mid-page in full-page shots.
